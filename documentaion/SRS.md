## 1. مقدمة

### 1.1 الغرض من الوثيقة

تهدف هذه الوثيقة إلى تحديد المتطلبات الوظيفية وغير الوظيفية لنظام إدارة المشاريع البرمجية باستخدام منهجية **Kanban**.

تمثل الوثيقة المرجع الأساسي لفريق التطوير خلال مراحل تحليل وتصميم وتنفيذ واختبار النظام، وتحدد بصورة واضحة ما يجب أن يقوم به النظام والقيود التي يجب أن يعمل ضمنها.

### 1.2 نطاق الوثيقة

تستهدف هذه الوثيقة:
- فريق التطوير (5 أعضاء)
- المشرف الأكاديمي
- المُقيِّمين

### 1.3 التعريفات والمصطلحات

| المصطلح | التعريف |
|---------|---------|
| **Kanban** | منهجية إدارة عمل تعتمد على أعمدة بصرية |
| **Task** | مهمة برمجية لها عنوان ووصف ومسؤول |
| **Sub-Task** | مهمة فرعية تابعة لمهمة رئيسية |
| **Sprint** | فترة زمنية محددة لإنجاز مهام |
| **PR** | Pull Request على GitHub |
| **BR** | Business Rule (قاعدة عمل) |
| **FR** | Functional Requirement (متطلب وظيفي) |
| **NFR** | Non-Functional Requirement (متطلب غير وظيفي) |

## 2. نظرة عامة على النظام

### 2.1 وصف النظام

النظام عبارة عن **تطبيق سطح مكتب** يسمح بإدارة مشاريع البرمجيات ومتابعة المهام المرتبطة بها.

يتيح النظام:
- إنشاء المشاريع وإضافة أعضاء إليها
- إنشاء مهام رئيسية وفرعية
- تحديد أولوية كل مهمة وموعدها
- إسنادها إلى أعضاء الفريق
- متابعة حالتها من خلال **لوحة Kanban**
- تسجيل العمليات المهمة من خلال **Activity Log**
- توليد تقارير عن التقدم والأداء

### 2.2 أهداف النظام

يجب أن يحقق النظام الأهداف التالية:

1. توفير وسيلة منظمة لإدارة مشاريع البرمجيات
2. إدارة أعضاء فرق المشاريع وصلاحياتهم
3. إنشاء وإدارة المهام المرتبطة بالمشاريع
4. دعم العلاقة الهرمية بين المهام الرئيسية والفرعية
5. توزيع المهام على أعضاء الفريق
6. متابعة سير العمل باستخدام Kanban Board
7. تسجيل التغييرات المهمة على المهام
8. حساب نسبة إنجاز المشاريع
9. عرض إحصائيات عن أداء أعضاء الفريق
10. ضمان سلامة البيانات أثناء العمليات متعددة الخطوات
11. توفير بنية برمجية قابلة للصيانة والتطوير
12. دعم التطوير الجماعي باستخدام Git و GitHub

## 6. المتطلبات الوظيفية

### 6.1 Authentication

#### FR-01 — تسجيل الدخول

**الوصف:** يجب أن يسمح النظام للمستخدم بتسجيل الدخول باستخدام اسم المستخدم وكلمة المرور.

**معايير القبول:**
- عند إدخال بيانات صحيحة، يتم السماح بالدخول
- عند إدخال بيانات خاطئة، يتم رفض الدخول وإظهار رسالة مناسبة
- لا يستطيع المستخدم الوصول إلى الوظائف المحمية دون تسجيل الدخول
- يتم تحديد صلاحيات المستخدم بناءً على دوره

---

### 6.2 User Management

#### FR-02 — إنشاء مستخدم

**الوصف:** يجب أن يستطيع Administrator إنشاء مستخدم جديد.

**بيانات المستخدم:**
- Username
- Full Name
- Email
- Password
- Role
- Active Status

**معيار القبول:** لا يتم إنشاء مستخدم جديد إذا كان اسم المستخدم مستخدماً مسبقاً.

#### FR-03 — تعديل المستخدم

**الوصف:** يجب أن يستطيع Administrator تعديل بيانات المستخدم وفق الصلاحيات.

#### FR-04 — تعطيل المستخدم

**الوصف:** يجب أن يستطيع Administrator تعطيل حساب المستخدم دون حذف سجله من قاعدة البيانات.

---

### 6.3 Project Management

#### FR-05 — إنشاء مشروع

**الوصف:** يجب أن يستطيع Project Leader إنشاء مشروع جديد.

**بيانات المشروع:**
- Project Name (إلزامي)
- Description
- Start Date
- Expected End Date
- Status
- Creator

**معايير القبول:**
- اسم المشروع إلزامي
- تاريخ النهاية المتوقع لا يجب أن يسبق تاريخ البداية
- يتم تسجيل منشئ المشروع

#### FR-06 — تعديل المشروع

**الوصف:** يجب أن يستطيع Project Leader تعديل بيانات المشروع.

#### FR-07 — عرض المشاريع

**الوصف:** يجب أن يستطيع المستخدم مشاهدة المشاريع التي يملك صلاحية الوصول إليها.

#### FR-08 — إدارة أعضاء المشروع

**الوصف:** يجب أن يستطيع Project Leader إضافة مستخدمين إلى المشروع وإزالتهم.

**قاعدة عمل:** لا يجوز إسناد مهمة إلى مستخدم ليس عضواً في المشروع.

---

### 6.4 Task Management

#### FR-09 — إنشاء مهمة

**الوصف:** يجب أن يستطيع المستخدم المخوّل إنشاء Task داخل مشروع.

**بيانات المهمة:**
- Title
- Description
- Project
- Parent Task
- Assigned User
- Priority
- Status
- Due Date
- Creator
- Creation Date

#### FR-10 — تعديل المهمة

**الوصف:** يجب أن يستطيع المستخدم المخوّل تعديل بيانات المهمة.

#### FR-11 — حذف المهمة

**الوصف:** يجب أن يستطيع المستخدم المخوّل حذف المهمة وفق قواعد النظام.

#### FR-12 — إسناد المهمة

**الوصف:** يجب أن يستطيع Project Leader إسناد المهمة إلى أحد أعضاء المشروع.

**معيار القبول:** يجب رفض عملية الإسناد إذا لم يكن المستخدم عضواً في المشروع.

---

### 6.5 Task Hierarchy

#### FR-13 — إنشاء Sub-Task

**الوصف:** يجب أن يسمح النظام بإنشاء مهمة فرعية مرتبطة بمهمة رئيسية.

**التمثيل:** باستخدام `ParentTaskID` الذي يشير إلى `TaskID` لمهمة أخرى.

**مثال:**
```
Develop Login
├── Design Login UI
├── Implement Authentication
└── Validate Credentials
```

#### FR-14 — عرض التسلسل الهرمي

**الوصف:** يجب أن يستطيع النظام عرض المهام الرئيسية والفرعية بطريقة واضحة.

#### FR-15 — التحقق من العلاقة الهرمية

**الوصف:** يجب منع إنشاء علاقة تؤدي إلى دورة غير صحيحة في شجرة المهام.

**مثال غير مسموح:**
```
Task A
└── Task B
    └── Task A  ← ممنوع!
```

---

### 6.6 Priorities

#### FR-16 — تحديد أولوية المهمة

**الوصف:** يجب أن يسمح النظام بتحديد إحدى الأولويات:
- High
- Medium
- Low

---

### 6.7 Task Due Dates

#### FR-17 — تحديد Due Date

**الوصف:** يجب أن يسمح النظام بتحديد موعد نهائي للمهمة.

**قاعدة عمل:** لا يجوز أن يكون Due Date قبل تاريخ إنشاء المهمة.

---

### 6.8 Kanban Board

#### FR-18 — عرض لوحة Kanban

**الوصف:** يجب أن يعرض النظام المهام ضمن ثلاثة أعمدة:
- New
- In Progress
- Done

#### FR-19 — تغيير حالة المهمة

**الوصف:** يجب أن يستطيع المستخدم المخوّل نقل المهمة بين حالات Kanban.

```
New → In Progress → Done
```

#### FR-20 — تحديث قاعدة البيانات

**الوصف:** عند تغيير حالة المهمة، يجب تحديث حالتها في قاعدة البيانات.

#### FR-21 — منع إكمال المهمة الرئيسية

**الوصف:** إذا كانت للمهمة الرئيسية مهام فرعية غير مكتملة، يجب على النظام منع تحويلها إلى "Done".

---

### 6.9 Activity Log

#### FR-22 — تسجيل نشاطات المهام

**الوصف:** يجب أن يسجل النظام العمليات المهمة:
- إنشاء المهمة
- تعديل المهمة
- حذف المهمة
- إسناد المهمة
- تغيير الحالة
- تغيير الأولوية

**يجب أن يتضمن السجل:**
- المستخدم المنفذ
- المهمة المرتبطة
- نوع العملية
- وصف العملية
- التاريخ والوقت

#### FR-23 — عرض Activity Log

**الوصف:** يجب أن يستطيع المستخدم المخوّل مشاهدة سجل النشاطات.

---

### 6.10 Reports

#### FR-24 — تقرير تقدم المشروع

**الوصف:** يجب أن يعرض النظام:
- إجمالي عدد المهام
- عدد المهام الجديدة
- عدد المهام قيد التنفيذ
- عدد المهام المنجزة
- نسبة الإنجاز الكلية

#### FR-25 — حساب نسبة الإنجاز

**الوصف:** يجب حساب نسبة الإنجاز بناءً على عدد المهام المنجزة من الإجمالي.

**المعادلة:**
```
نسبة الإنجاز = (المهام المنجزة ÷ إجمالي المهام) × 100
```

#### FR-26 — تقرير أداء أعضاء الفريق

**الوصف:** يجب أن يعرض النظام عدد المهام المنجزة لكل عضو.

## 7. المتطلبات غير الوظيفية

### NFR-01 — Architecture
يجب بناء النظام باستخدام **3-Tier Architecture**:
- Presentation Layer
- Business Logic Layer
- Data Access Layer

### NFR-02 — Maintainability
- الكود منظم وقابل للصيانة
- عدم وضع SQL Queries مباشرة داخل Forms

### NFR-03 — Security
- عدم تخزين كلمات المرور كنص صريح
- استخدام Hashing آمن (PBKDF2)
- تطبيق صلاحيات الوصول حسب الدور

### NFR-04 — Data Integrity
- استخدام Primary Keys و Foreign Keys
- استخدام Constraints و Validation
- استخدام Transactions للعمليات متعددة الخطوات

### NFR-05 — Transaction Safety
عند تنفيذ عمليات مترابطة، يجب تنفيذها ضمن Transaction واحدة:
- نجاح جميع العمليات معاً
- أو التراجع عنها جميعاً عند حدوث خطأ

### NFR-06 — Performance
- استجابة سريعة للعمليات
- عدم تنفيذ استعلامات غير ضرورية

### NFR-07 — Usability
- واجهات واضحة ومنظمة
- خصوصاً Kanban Board وإدارة المهام

### NFR-08 — Reliability
- معالجة الأخطاء المتوقعة
- عدم إغلاق التطبيق بشكل غير متوقع
- رسائل خطأ مفهومة

### NFR-09 — Scalability
- تصميم قابل للتوسع
- إضافة مشاريع ومستخدمين ومهام جديدة دون إعادة البناء

### NFR-10 — Collaboration
- تطوير باستخدام Git و GitHub
- استخدام Branches و PRs و Code Reviews

## 8. قواعد العمل (Business Rules)

| الرمز | القاعدة |
|-------|---------|
| **BR-01** | كل Project يجب أن يمتلك منشئاً محدداً |
| **BR-02** | لا يجوز إسناد Task إلى مستخدم غير عضو في المشروع |
| **BR-03** | كل Task يجب أن تنتمي إلى Project واحد |
| **BR-04** | يمكن للمهمة أن تكون Main Task أو Sub-Task |
| **BR-05** | `ParentTaskID = NULL` يعني أن المهمة رئيسية |
| **BR-06** | `ParentTaskID` غير NULL يعني أن المهمة Sub-Task |
| **BR-07** | لا يجوز إنشاء علاقة هرمية دائرية |
| **BR-08** | لا يجوز إكمال Main Task إذا كانت لديها Sub-Tasks غير مكتملة |
| **BR-09** | كل تغيير مهم على المهمة يجب أن يُسجل في Activity Log |
| **BR-10** | لا يستطيع المستخدم تنفيذ وظيفة لا يمتلك صلاحيتها |

## 14. الخلاصة

**المحاور الرئيسية:**
```
Projects → Tasks & Task Hierarchy → Kanban Workflow
```

**مع دعم:**
```
Users & Roles → Project Members → Task Assignment → Activity Tracking → Progress Reports
```

النظام مطبق باستخدام:
- **C# / Windows Forms** للواجهات
- **SQL Server** لقاعدة البيانات
- **3-Tier Architecture** للبنية
