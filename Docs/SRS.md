# متطلبات نظام إدارة المشاريع البرمجية باستخدام Kanban

**اسم المشروع:** Kanban Project Management System  
**نوع الوثيقة:** Software Requirements Specification (SRS)  
**الإصدار:** 1.0  
**نوع التطبيق:** تطبيق سطح مكتب (Desktop)  
**المنصة المستهدفة:** Windows  
**التقنيات:** C# / Windows Forms / SQL Server  
**المعمارية:** 3-Tier Architecture  
**نموذج التطوير:** تطوير جماعي باستخدام Git و GitHub

---

## 1. مقدمة

### 1.1 الغرض من الوثيقة

تهدف هذه الوثيقة إلى تحديد المتطلبات الوظيفية وغير الوظيفية لنظام إدارة المشاريع البرمجية باستخدام منهجية Kanban.

تمثل الوثيقة المرجع الأساسي لفريق التطوير خلال مراحل تحليل وتصميم وتنفيذ واختبار النظام، وتحدد بصورة واضحة ما يجب أن يقوم به النظام والقيود التي يجب أن يعمل ضمنها.

يستهدف النظام فرق تطوير البرمجيات التي تحتاج إلى إدارة المشاريع والمهام، توزيع العمل بين أعضاء الفريق، ومتابعة تقدم التنفيذ من خلال لوحة Kanban.

---

## 2. نظرة عامة على النظام

### 2.1 وصف النظام

النظام عبارة عن تطبيق سطح مكتب يسمح بإدارة مشاريع البرمجيات ومتابعة المهام المرتبطة بها.

يتيح النظام إنشاء المشاريع وإضافة أعضاء إليها، وإنشاء مهام رئيسية وفرعية، وتحديد أولوية كل مهمة وموعدها، وإسنادها إلى أعضاء الفريق، ثم متابعة حالتها من خلال لوحة Kanban.

كما يوفر النظام تقارير عن تقدم المشروع وأداء أعضاء الفريق، ويسجل العمليات المهمة التي تتم على المهام من خلال **Activity Log**.

---

## 3. أهداف النظام

يجب أن يحقق النظام الأهداف التالية:

1. توفير وسيلة منظمة لإدارة مشاريع البرمجيات.
2. إدارة أعضاء فرق المشاريع وصلاحياتهم.
3. إنشاء وإدارة المهام المرتبطة بالمشاريع.
4. دعم العلاقة الهرمية بين المهام الرئيسية والفرعية.
5. توزيع المهام على أعضاء الفريق.
6. متابعة سير العمل باستخدام Kanban Board.
7. تسجيل التغييرات المهمة على المهام.
8. حساب نسبة إنجاز المشاريع.
9. عرض إحصائيات عن أداء أعضاء الفريق.
10. ضمان سلامة البيانات أثناء تنفيذ العمليات متعددة الخطوات.
11. توفير بنية برمجية قابلة للصيانة والتطوير.
12. دعم التطوير الجماعي باستخدام Git و GitHub.

### 4.2 Project Leader

المسؤول عن إدارة المشاريع والفرق والمهام ومتابعة تقدم المشروع.

### 4.3 Team Member

## 7. المتطلبات الوظيفية

### 7.1 Authentication

**FR-01 — تسجيل الدخول**

يجب أن يسمح النظام للمستخدم بتسجيل الدخول باستخدام اسم المستخدم وكلمة المرور.

**معايير القبول:**
- عند إدخال بيانات صحيحة، يتم السماح بالدخول.
- عند إدخال بيانات خاطئة، يتم رفض الدخول وإظهار رسالة مناسبة.
- لا يستطيع المستخدم الوصول إلى الوظائف المحمية دون تسجيل الدخول.
- يتم تحديد صلاحيات المستخدم بناءً على دوره.

### 7.2 User Management

**FR-02 — إنشاء مستخدم**

يجب أن يستطيع Administrator إنشاء مستخدم جديد.

يجب أن تتضمن بيانات المستخدم:
- Username.
- Full Name.
- Email.
- Password.
- Role.
- Active Status.

**معيار القبول:** لا يتم إنشاء مستخدم جديد إذا كان اسم المستخدم مستخدمًا مسبقًا.

**FR-03 — تعديل المستخدم**

يجب أن يستطيع Administrator تعديل بيانات المستخدم وفق الصلاحيات.

**FR-04 — تعطيل المستخدم**

يجب أن يستطيع Administrator تعطيل حساب المستخدم دون حذف سجله من قاعدة البيانات.

---

## 8. إدارة المشاريع

**FR-05 — إنشاء مشروع**

يجب أن يستطيع Project Leader إنشاء مشروع جديد.

بيانات المشروع:
- Project Name.
- Description.
- Start Date.
- Expected End Date.
- Status.
- Creator.

**معايير القبول:**
- اسم المشروع إلزامي.
- تاريخ النهاية المتوقع لا يجب أن يسبق تاريخ البداية.
- يتم تسجيل منشئ المشروع.
- يتم إنشاء المشروع بنجاح فقط عند اجتياز قواعد التحقق.

**FR-06 — تعديل المشروع**

يجب أن يستطيع Project Leader تعديل بيانات المشروع وفق الصلاحيات.

**FR-07 — عرض المشاريع**

يجب أن يستطيع المستخدم مشاهدة المشاريع التي يملك صلاحية الوصول إليها.

**FR-08 — إدارة أعضاء المشروع**

يجب أن يستطيع Project Leader إضافة مستخدمين إلى المشروع وإزالتهم.

**قاعدة عمل:** لا يجوز إسناد مهمة إلى مستخدم ليس عضوًا في المشروع.

---

## 9. إدارة المهام

**FR-09 — إنشاء مهمة**

يجب أن يستطيع المستخدم المخول إنشاء Task داخل مشروع.

بيانات المهمة الأساسية:
- Title.
- Description.
- Project.
- Parent Task.
- Assigned User.
- Priority.
- Status.
- Due Date.
- Creator.
- Creation Date.

**FR-10 — تعديل المهمة**

يجب أن يستطيع المستخدم المخول تعديل بيانات المهمة.

**FR-11 — حذف المهمة**

يجب أن يستطيع المستخدم المخول حذف المهمة وفق قواعد النظام.

**FR-12 — إسناد المهمة**

يجب أن يستطيع Project Leader إسناد المهمة إلى أحد أعضاء المشروع.

**معيار القبول:** يجب رفض عملية الإسناد إذا لم يكن المستخدم عضوًا في المشروع.

---

## 10. التسلسل الهرمي للمهام (Task Hierarchy)

**FR-13 — إنشاء Sub-Task**

يجب أن يسمح النظام بإنشاء مهمة فرعية مرتبطة بمهمة رئيسية.

يتم تمثيل العلاقة باستخدام `ParentTaskID` بحيث يشير الحقل إلى `TaskID` لمهمة أخرى داخل جدول Tasks.

**مثال:**
Develop Login
|----- Design Login UI
|----- Implement Authentication
|----- Validate Credentials
**FR-14 — عرض التسلسل الهرمي**

يجب أن يستطيع النظام عرض المهام الرئيسية والفرعية بطريقة واضحة.

**FR-15 — التحقق من العلاقة الهرمية**

يجب منع إنشاء علاقة تؤدي إلى دورة غير صحيحة في شجرة المهام.

**مثال غير مسموح:**
Task A
|_______ Task B
|_______ Task A

## 12. مواعيد المهام

**FR-17 — تحديد Due Date**

يجب أن يسمح النظام بتحديد موعد نهائي للمهمة.

**قاعدة عمل:** لا يجوز أن يكون Due Date قبل تاريخ إنشاء المهمة، ما لم يسمح النظام بذلك في حالات خاصة يحددها Project Leader.

## 13. لوحة Kanban

**FR-18 — عرض لوحة Kanban**

يجب أن يعرض النظام المهام ضمن ثلاثة أعمدة:
- New
- In Progress
- Done

**FR-19 — تغيير حالة المهمة**

يجب أن يستطيع المستخدم المخول نقل المهمة بين حالات Kanban.

**FR-20 — تحديث قاعدة البيانات**

عند تغيير حالة المهمة، يجب أن يتم تحديث حالة المهمة في قاعدة البيانات.

**FR-21 — منع إكمال المهمة الرئيسية قبل اكتمال المهام الفرعية**

إذا كانت للمهمة الرئيسية مهام فرعية غير مكتملة، فيجب على النظام منع تحويل المهمة الرئيسية إلى "Done".

يجب أن يسجل النظام العمليات المهمة التي تتم على المهام.

من أمثلتها:
- إنشاء المهمة.
- تعديل المهمة.
- حذف المهمة.
- إسناد المهمة.
- تغيير الحالة.

- المستخدم المنفذ للعملية.
- المهمة المرتبطة.
- نوع العملية.
- وصف العملية.
- التاريخ والوقت.

**FR-23 — عرض Activity Log**

يجب أن يستطيع المستخدم المخول مشاهدة سجل النشاطات المرتبط بالمشروع أو المهمة.

## 16. المتطلبات غير الوظيفية

**NFR-01 — Architecture**

يجب بناء النظام باستخدام 3-Tier Architecture للفصل بين:
- Presentation Layer.
- Business Logic Layer.
- Data Access Layer.

**NFR-02 — Maintainability**

يجب أن يكون الكود منظمًا وقابلًا للصيانة والتطوير. يجب عدم وضع SQL Queries مباشرة داخل Forms.

**NFR-03 — Security**

يجب عدم تخزين كلمات المرور بصورتها النصية المباشرة. يجب تخزين قيمة آمنة مشتقة من كلمة المرور باستخدام آلية Hashing مناسبة. كما يجب تطبيق صلاحيات الوصول بناءً على دور المستخدم.

**NFR-04 — Data Integrity**

يجب الحفاظ على اتساق البيانات باستخدام:
- Primary Keys.
- Foreign Keys.
- Constraints.
- Validation.
- Transactions عند تنفيذ العمليات متعددة الخطوات.

**NFR-05 — Transaction Safety**

عند تنفيذ عملية تتطلب أكثر من تعديل مترابط، مثل تغيير حالة المهمة وتسجيل النشاط، يجب تنفيذ العمليات ضمن Transaction واحدة بحيث:
- تنجح جميع العمليات معًا.
- أو يتم التراجع عنها جميعًا عند حدوث خطأ.

**NFR-06 — Performance**

يجب أن يستجيب النظام للعمليات الاعتيادية مثل فتح القوائم وحفظ البيانات خلال فترة زمنية مناسبة للاستخدام المكتبي، وألا ينفذ استعلامات غير ضرورية على قاعدة البيانات.

**NFR-07 — Usability**

يجب أن تكون الواجهات واضحة ومنظمة، خصوصًا Kanban Board وإدارة المهام.

**NFR-08 — Reliability**

يجب معالجة الأخطاء المتوقعة دون إغلاق التطبيق بشكل غير متوقع، مع عرض رسائل مفهومة للمستخدم.

**NFR-09 — Scalability**

يجب تصميم قاعدة البيانات والطبقات البرمجية بحيث يمكن إضافة مشاريع ومستخدمين ومهام جديدة دون إعادة بناء النظام بالكامل.

**NFR-10 — Collaboration**

يجب تطوير المشروع باستخدام Git و GitHub، بحيث يستطيع أعضاء الفريق الخمسة العمل بالتوازي باستخدام Branches و Pull Requests و Code Reviews و Merge.

## 17. قواعد العمل (Business Rules)

**BR-01**  
كل Project يجب أن يمتلك منشئًا محددًا.

**BR-02**  
لا يجوز إسناد Task إلى مستخدم غير عضو في المشروع.

**BR-03**  
كل Task يجب أن تنتمي إلى Project واحد.

**BR-04**  
يمكن للمهمة أن تكون Main Task أو Sub-Task.

**BR-05**  
`ParentTaskID = NULL` يعني أن المهمة مهمة رئيسية.

**BR-06**  
`ParentTaskID` غير NULL يعني أن المهمة Sub-Task.

**BR-07**  
لا يجوز إنشاء علاقة هرمية دائرية بين المهام.

**BR-08**  
لا يجوز إكمال Main Task إذا كانت لديها Sub-Tasks غير مكتملة.

**BR-09**  
كل تغيير مهم على المهمة يجب أن يسجل في Activity Log.

**BR-10**  
لا يستطيع المستخدم تنفيذ وظيفة لا يمتلك صلاحيتها.

## 18. القيود (Constraints)

### 18.1 قيود تقنية

النظام هو تطبيق Desktop يعمل على Windows.

التقنيات الأساسية:
- **Programming Language:** C#
- **UI Framework:** Windows Forms
- **Database:** Microsoft SQL Server
- **Architecture:** 3-Tier
- **Version Control:** Git
- **Repository:** GitHub

### 18.2 قيود المشروع

- المشروع أكاديمي.
- يتم تطويره بواسطة فريق من خمسة أعضاء.
- يجب أن تكون مساهمة أعضاء الفريق قابلة للتتبع عبر Git/GitHub.
- يجب الحفاظ على بنية المشروع المنظمة.
- يجب ألا تؤدي إضافة ميزة جديدة إلى كسر الوظائف الموجودة.

---

## 19. الافتراضات

يفترض النظام ما يلي:

1. يوجد اتصال متاح بقاعدة SQL Server عند تشغيل النظام.
2. المستخدم لديه حساب صالح في النظام.
3. المستخدم ينتمي إلى المشاريع التي يستطيع الوصول إليها.
4. Project Leader مسؤول عن تنظيم أعضاء المشروع ومهامه.
5. البيانات المدخلة من المستخدم يجب أن تخضع للتحقق قبل تخزينها.
6. المشروع يعمل ضمن بيئة Windows.
7. GitHub يستخدم لإدارة الكود وليس كمصدر مباشر لبيانات النظام في الإصدار الأول.

## 21. معايير النجاح

يعتبر المشروع ناجحًا عند تحقق المعايير التالية:

### Functional Success
- يستطيع المستخدم تسجيل الدخول.
- يتم تطبيق الصلاحيات بصورة صحيحة.
- يمكن إنشاء المشاريع وتعديلها.
- يمكن إضافة أعضاء للمشاريع.
- يمكن إنشاء المهام وتعديلها.
- يمكن إنشاء Sub-Tasks.
- تعمل علاقة `ParentTaskID` بصورة صحيحة.
- يمكن إسناد المهام لأعضاء المشروع.
- تعمل Kanban Board بالحالات الثلاث.
- يمكن تغيير حالة المهمة.
- يتم تسجيل النشاطات.
- يتم حساب نسبة الإنجاز.
- تعرض التقارير بيانات صحيحة.

### Technical Success
- تطبيق 3-Tier Architecture بصورة واضحة.
- استخدام SQL Server.
- تطبيق Foreign Keys والعلاقات.
- استخدام Transactions في العمليات المطلوبة.
- تطبيق Validation في Business Logic.
- عدم وضع منطق قاعدة البيانات داخل واجهات المستخدم.

### Collaboration Success
يجب أن يظهر في GitHub:
- Repository منظم.
- Branches متعددة.
- Commits حقيقية من أعضاء الفريق.
- Issues موزعة على أعضاء الفريق.
- Pull Requests.
- Code Reviews.
- Merges.
- معالجة Merge Conflicts عند حدوثها.
- مساهمة فعلية من أعضاء الفريق الخمسة.

## 22. قابلية اختبار المتطلبات

يجب أن يكون كل Requirement قابلًا للتحقق من خلال الاختبار.

**مثال: FR-12 — إسناد المهمة**

**Test Case 1:**
- **Given:** المشروع يحتوي على Ahmed كعضو.
- **When:** يقوم Project Leader بإسناد Task إلى Ahmed.
- **Then:** يتم حفظ AssignedTo بنجاح.

**Test Case 2:**
- **Given:** Mohammad ليس عضوًا في المشروع.
- **When:** يحاول Project Leader إسناد Task إليه.
- **Then:** يرفض النظام العملية ويعرض رسالة مناسبة.

وهذا الأسلوب سيستخدم لاحقًا عند كتابة Test Cases للمشروع.
